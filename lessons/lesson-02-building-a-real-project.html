Chapter 1

Fork vs Clone

Both commands download a GitHub repo. The difference is who owns what — and what you can do with it afterwards.

📋 git clone

Downloads a repo to your computer. The remote still points at the original owner's GitHub. You can't push changes back unless they gave you permission.

🍴 Fork

Copies the repo to your GitHub account first. Then you clone your fork. You now own it, can push freely, and the original source is completely separate.

The Ownership Diagram

── Clone (Access, not Ownership) ────────────────────────────────── github.com/original/repo ↓ git clone Your Computer (remote = original owner's GitHub) → You can't push. You're borrowing it. ── Fork (Ownership) ──────────────────────────────────────────────── github.com/original/repo ↓ Fork on GitHub github.com/YOU/repo ← your own copy in the cloud ↓ git clone Your Computer (remote = YOUR GitHub) → Full ownership. Push, modify, build freely.

When to Use Each

Goal What to do
Just run it locally and explore Clone directly
Make it your own and build on top of it Fork first, then clone your fork
Contribute back to the original project Fork → make changes → open a Pull Request
Completely independent copy — no link to original Clone → delete .git → git init → push to new repo
The Practical Rule

If you want to own and build something — fork first. If you just want to read or run it — clone is fine.

The "Fully Independent Copy" Method

Fork still shows "forked from original/repo" on your GitHub. If you want zero connection to the source — use this three-step method:

# 1. Clone the repo you want
git clone https://github.com/someuser/some-repo

# 2. Delete its git history (remove .git folder)
Remove-Item -Recurse -Force some-repo/.git

# 3. Re-initialize and push to your own new repo
cd some-repo
git init
git remote add origin https://github.com/YOU/your-new-repo
git add .
git commit -m "Initial commit"
git push -u origin master

Chapter 2

Claude & Multiple Projects

Claude works best when it's opened directly inside the project folder it's going to work on. Here's why — and how to manage it.

How Claude Knows Which Project You're In

When you launch Claude Code from a folder, it reads that folder's git context, file structure, and any CLAUDE.md file it finds there. This is how it understands your project automatically without you having to re-explain it every session.

── Claude opened from ClaudeTut/ ─────────────────────────────────── Reads: ClaudeTut/CLAUDE.md ✓ sees learning project context Git: github.com/AdamVisutag/ClaudeTut Memory: lesson history, learner profile ── Claude opened from RVolumetrics_Dev/ ──────────────────────────── Reads: RVolumetrics_Dev/CLAUDE.md ✓ sees Recon Volumetrics context Git: github.com/AdamVisutag/ReconVolumetrics Memory: product spec, tech stack, dev context
One Project Per Session

You can technically work on another folder from within any session — but Claude's git commands, file paths, and context will be anchored to where it was opened. For serious work: open Claude in the target project folder.

The Practical Setup for Recon Volumetrics

1

Open a terminal in the project folder

Navigate to C:\ReconVolumetrics\RVolumetrics_Dev and launch Claude from there.

2

Claude auto-reads CLAUDE.md

The product context, terminology, and priorities are all loaded automatically — no need to re-explain the project.

3

Claude auto-reads DEV_CONTEXT.md

The tech stack decisions, implementation order, and current state are available from the first message.

The Principle Behind This

Every project gets its own memory layer — its git history, its CLAUDE.md, its DEV_CONTEXT.md. When you launch Claude in that folder, all of it is immediately in context. You never start from zero.

Chapter 3

Giving Claude Lasting Context

Claude has no memory between sessions by default. Two files change that — CLAUDE.md and DEV_CONTEXT.md. These are the most important files in any project you build AI-assisted.

CLAUDE.md — The Product Brain

This file sits at the root of your project and is automatically loaded by Claude Code at the start of every session. Think of it as a permanent instruction card that tells Claude what this project is and what matters.

Put in CLAUDE.md Why
What the product does So Claude makes decisions aligned with your vision, not generic code
Who the users are So UI and feature decisions fit the audience
What's in scope for MVP So Claude doesn't over-engineer or go off-track
Key terminology So Claude uses the right words (e.g. "Scene" not "3D file")
Strategic positioning So Claude understands what you are and are NOT building

DEV_CONTEXT.md — The Technical Brain

A second file for purely technical decisions. While CLAUDE.md is product and business context, DEV_CONTEXT.md is the developer's reference — written so you can open VS Code and pick up exactly where you left off.

CLAUDE.md

What are we building? For whom? What does "done" look like? Product-first context that shapes every decision.

DEV_CONTEXT.md

Tech stack, install commands, folder structure, what's been built, what's next. Developer-facing reference for every session.

Providing Files as Context (PDFs, Images)

Claude can read any file in your project folder. To give Claude access to planning documents:

1

Drop the files directly into the project folder

PDFs, images, spreadsheets — just drag them in. If they're there, Claude can read them.

2

Commit them to git

They become part of the repo. Any session (and any collaborator) can reference them.

3

Point Claude to them in CLAUDE.md

Add a line like: "Planning documents are in Planning Files/" — Claude will know to read them for context.

What We Did for Recon Volumetrics

Added three PDFs and a UX mockup PNG to Planning Files/. Claude read all four, then explained the full product concept back in plain language — confirming it understood the vision before any code was written.

Chapter 4

Starting a New Project from Scratch

How to go from an empty folder to a live GitHub repo with your first meaningful commit — the exact steps used to launch Recon Volumetrics.

The Full Setup Sequence

1

Create the repo on GitHub first

Go to github.com → New repository. Name it, set it to private, skip adding files (you'll push from local).

2

Initialize git in your local folder

git init — run this inside the project folder. This creates the .git history tracker.

3

Connect local to GitHub

git remote add origin <url> — links your local repo to the GitHub repo you just created.

4

Add your context files and commit

Add CLAUDE.md, DEV_CONTEXT.md, planning files — then commit with a message that marks this as the starting point.

5

Push to GitHub

git push -u origin master — uploads everything and sets the upstream tracking branch.

# Inside your project folder
git init
git remote add origin https://github.com/AdamVisutag/ReconVolumetrics

# Stage everything and make the first commit
git add .
git commit -m "Initial commit: planning docs, CLAUDE.md — MVP starting point"

# Push to GitHub and set the tracking branch
git push -u origin master

The .gitignore File

Some things should never go to GitHub — private config, Claude's internal settings, API keys. The .gitignore file tells git what to skip.

Entry What it excludes
.claude/ Claude Code's local settings — machine-specific, not for sharing
node_modules/ npm packages — huge folder, regenerated with npm install
.env Environment variables — secrets like API keys, database URLs
.next/ Next.js build output — generated during build, not source code
First Commit Message Matters

The first commit message is a permanent marker in your history. Write one that clearly marks what this is and what state it's in. You'll thank yourself in six months when scrolling the log.

Chapter 5

Planning a Tech Stack

The technology choices you make before writing a single line of code shape everything. Here's the stack we chose for Recon Volumetrics — and why each piece was selected.

The Chosen Stack

Next.js 15
Framework

The industry-standard React framework. Handles routing, page structure, and project organization. AI tools generate accurate Next.js code reliably — making Claude more useful.

TypeScript
Language

JavaScript with type safety. Catches errors before they run. Especially important in a complex platform with many moving parts.

Tailwind CSS
Styling

Utility-first CSS that makes responsive layouts straightforward. Desktop 3-panel → mobile stacked view is handled by adding breakpoint classes like md:flex-row.

shadcn/ui
UI Components

Dark-theme component library built for Next.js + Tailwind. Buttons, panels, tables, tabs, dialogs — all dark and professional out of the box. Components are copy-pasted into your project (fully customizable).

Three.js + GaussianSplats3D
3D Viewer

Three.js is the standard WebGL 3D library. @mkkellogg/GaussianSplats3D renders Gaussian splat .ply/.splat files in the browser — the core visual feature of the platform.

Zustand
State Management

Lightweight shared state (current site, active scan, selected scene). Minimal boilerplate — far simpler than Redux.

The Layout Architecture

── Desktop (md and above) ────────────────────────────────────────── ┌──────┬──────────────────────────────┬──────────┐ │ Side │ 3D Viewer │ Data │ │ Nav │ (GaussianSplats3D) │ Panels │ │ ├──────────────────────────────┤ Reports │ │ │ Timeline Bar │ Media │ └──────┴──────────────────────────────┴──────────┘ ── Mobile (below md — same code, stacked) ────────────────────────── ┌─────────────────────┐ │ Top Nav Bar │ ├─────────────────────┤ │ 3D Viewer │ ├─────────────────────┤ │ Timeline Bar │ ├─────────────────────┤ │ Scene Browser │ ├─────────────────────┤ │ Data Panels │ └─────────────────────┘
One Codebase, Two Layouts

Tailwind handles the entire responsive shift with a single breakpoint class. The same components render as a side-by-side dashboard on desktop and a stacked single column on mobile — no separate mobile codebase needed.

Chapter 6

Setting Up Next.js

What it took to go from zero to a running Next.js dev server — including the obstacles we hit and how they were solved.

Prerequisites

Next.js 15 requires Node.js version 18 or higher. Node.js is the runtime that executes JavaScript outside the browser — it powers npm, the package manager used to install everything.

# Check your Node.js version
node --version

# If below v18, install the latest LTS via Windows Package Manager
winget install OpenJS.NodeJS.LTS

# Confirm after install (open a new terminal)
node --version   # should show v24.x.x or similar

Scaffolding the App

create-next-app sets up the entire project structure — TypeScript config, Tailwind CSS, ESLint, App Router, folder structure — in one command.

# Scaffold a new Next.js app (run from the parent directory)
npx create-next-app@latest recon-volumetrics

# When prompted, select:
#   TypeScript   → Yes
#   ESLint       → Yes
#   Tailwind CSS → Yes
#   App Router   → Yes
#   Turbopack    → Yes (faster dev server)

# Start the dev server
npm run dev

Obstacles We Hit (and Solved)

Problem Cause Fix
Node.js v16 — too old Next.js 15 requires Node 18+. Old version was v16.16.0 Installed Node.js v24.15.0 via winget
npm naming restriction npm forbids capital letters in package names. Folder was named RVolumetrics_Dev Scaffolded in parent dir as recon-volumetrics, moved files, updated package.json
PATH not updated after install Terminal session didn't pick up new Node.js path Used full path to npm.cmd / npx.cmd, or opened a new terminal

Summary & Cheat Sheet

Everything from this session in one place.

Key Mental Models

  • Clone = borrow. Fork = own. For building on top of something, fork first.
  • Open Claude inside the project folder — that's how it loads the right context automatically.
  • CLAUDE.md = the product brain. Every session, Claude reads it first. Write it once, benefit forever.
  • DEV_CONTEXT.md = the technical brain. Current state, tech stack, what's next. Your VS Code session anchor.
  • You can drop any file (PDF, image, doc) into the project folder — Claude can read it as context.
  • Starting a project: git init → connect remote → commit context files → push.
  • npm package names cannot contain capital letters. Use lowercase with hyphens.
  • Always check your Node.js version before scaffolding — frameworks have minimum requirements.
